# 規格審查報告 (Specification Review)

在測試與開發前對原規格書進行靜態分析，針對規格中模糊、矛盾與缺漏之處彙整如下。建議於開發前與 Product Owner (PO) / PM 召開 Kick-off 會議進行規格釐清：

### 1. 欄位輸入限制與驗證邊界模糊
* **姓名欄位 (Name)**：
  * **長度限制**：未定義字數上限與下限（如限制 2-50 字）。
  * **字元限制**：未說明是否允許輸入數字、英文、特殊符號、全形空白、Emoji 或 HTML 標籤（潛在 XSS 漏洞）。
* **Email 欄位**：
  * **驗證強度**：僅註明「需驗證格式」，未定義驗證正則表達式 (Regex) 的嚴格度（例如是否需阻擋連續點號 `user@domain..com` 或無效頂級域名）。
* **報名人數 (Attendees)**：
  * **UI 元件型態**：未指定為「下拉選單」或是「數字輸入框 (`<input type="number">`)」。
  * **防呆機制**：若為輸入框，未定義是否需阻擋鍵盤輸入小數點（如 1.5）、科學記號（如 `e`）與負數。

### 2. UI/UX 互動與錯誤處理機制未定義
* **錯誤訊息呈現方式**：
  * **提示位置**：規格僅提及「顯示對應錯誤訊息」，未明確定義呈現形式（如欄位下方紅字 inline message、頁面頂部 Toast / Banner，或是瀏覽器 Alert 彈窗）。
  * **觸發時機**：未定義驗證觸發時間點（為輸入時即時 `onInput` 驗證、離焦 `onBlur` 驗證，或是僅在點擊「送出按鈕」時統一驗證）。
* **票種切換行為 (Ticket Switch)**：
  * **狀態殘留**：當使用者先選擇「付費票」並輸入人數（此時顯示總金額），隨後切換為「免費票」時，金額顯示區塊應為「隱藏」還是「金額歸零」？若再次切回「付費票」，先前輸入的人數與金額是否保留？
* **表單預設值**：
  * **預設選項**：未定義票種下拉選單的預設選項（是預設選中「免費票」，還是需提供無效預設值如「-- 請選擇票種 --」以利必填驗證）。

### 3. 系統狀態與送出邏輯
* **表單送出後的行為**：
  * **欄位重置**：成功顯示「報名成功」後，表單欄位是否需要自動清空 (Reset)？
  * **防重複送出**：送出後是否需將「送出報名」按鈕設為 Disable，避免使用者連續點擊產生重複報名？
* **金額格式化**：
  * **顯示樣式**：金額是否需要千分位符號（例如 `NT$ 5,000` 或 `NT$ 5000`）？
